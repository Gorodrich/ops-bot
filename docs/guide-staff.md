# OpsBot 運営向けガイド

OpsBot（運営業務支援Bot）のコマンド一覧と、その裏側の仕組みをまとめたものです。各コマンドについて、まず「かんたん説明」（普段の運用で使う分にはこれだけ読めば十分）を書き、続けて「詳細」（参加者から仕様を聞かれたときにそのまま答えられる粒度）を書いています。

**上から順に読めば、どの機能をいつ使うか・裏で何が起きているかが分かるようにしてあります。** まず「0. 設計思想」「用語集」「場面別クイックリファレンス」に目を通してから、必要なコマンドの節を読んでください。

> **表記について**
> - コマンドはすべて「/」から始まるスラッシュコマンドです（例：`/modvote start`）。
> - 設定値（チャンネルID・締切時間・重みなど）はハードコードせず、D1の `settings` テーブルで管理しています。この文書では実際の数値ではなく設定キー名（例：`settings.deadlines.vote_hours`）で参照します。**現在値は運営内で共有してください。**
> - 「ephemeral（エフェメラル）」＝そのコマンドやボタンを押した本人にだけ見える一時メッセージ。秘密投票の秘密性はこれで担保しています。

## 0. 押さえておくべき設計思想

この4つを理解していれば、参加者からの「Botって何を勝手に決めてるの？」系の質問にはほぼ答えられます。

- **機械的に判定できることはLLMを使わない。** 面積計算・重複判定・期限判定・票の集計・通知・督促は、すべて通常のプログラムで動いています。LLMは「機械的には判定しづらいものの検出・判断」（チケット内容の要約、タスク自動割当のタイブレークなど）にしか使いません。
- **LLM層が止まっても他の機能は止まりません（縮退運転）。** 申請受付・投票・許可・督促・台帳はLLM抜きで完結します。`/ops llm` で一時停止・再開できます。
- **Botは賛否を代行しません。** 承認・却下・処罰・許可はすべて人間（運営または参加者）の入力が起点です。唯一の例外は個人開発領のBot形式審査で、これも「機械的に一意に判定できる範囲」に限定しています。
- **秘密投票・記名許可・Bot形式審査は性質の違う別モジュールです。** 混同しないでください（次の用語集参照）。

## 用語集

参加者に説明するときにも使う中心的な言葉です。

| 用語 | 意味 |
|---|---|
| **類型A ＝ 秘密投票** | 誰が賛成・反対したか分からない匿名投票。運営内の承認は `/modvote`、参加者の承認は `/vote`。ボタンへの応答がephemeralなので秘密性が保たれます。（名前が紛らわしいですが `/vote` が参加者用、`/modvote` が運営用です。） |
| **類型B ＝ 記名許可** | 誰がOK/NGを出したかが**公開・永久記録**される記名式の許可。`/kyoka`（運営内の許可）と `/umetate`（海の埋立て許可）。 |
| **Bot形式審査** | 機械的に一意に判定できる案件を、Botがその場で承認・却下する仕組み。個人開発領の `/kaihatsu` の単独申請・全削除だけが対象。 |
| **宣言型モデル** | `/kaihatsu set` の画像は「その人の個人開発領の全体」を表す。今回の画像に含まれない従前の範囲は削除として扱う方式。 |
| **ゾーン画像** | 開発範囲を「1ピクセル＝1ブロック」で塗った画像。面積・重複はこの不透明ピクセル集合で機械判定する。 |
| **休暇制度** | 運営者が `/staff leave` で登録する。休暇中は `/modvote`・`/vote` の母数から除外される。**運営者専用の制度**で、参加者投票の母数には影響しない。 |
| **共同確認（cosign）** | 論争性の高いタスクに次点候補を第2の担当者として自動追加し、両者の完了操作で初めて正式完了とする仕組み。 |

## 1. `/kaihatsu`（個人開発領の届出）— 参加者コマンド、運営が仕組みを把握しておくもの

**かんたん説明**：参加者が個人開発領を届け出るコマンド群です。**単独の申請はBotが自動で審査・承認します**（Bot形式審査）。複数人分をまとめて扱う「代表者一括申請」「同時処理グループ」の2つの特殊経路があり、これらは仮の状態を経て、本人確認や締切操作で確定します。運営が能動的に触るのは**撤回**と**仮承認の確認フォロー**くらいです。

### サブコマンド

| サブコマンド | 何をするか | 審査 |
|---|---|---|
| `set` | 個人開発領の設定・変更の届出（画像添付） | 単独なら即時Bot形式審査。複数人分は仮承認 or グループ蓄積 |
| `delete` | 個人開発領の削除の届出 | 自分・グループなしの全削除は即時Bot形式審査 |
| `list` | 本人の登録状況（面積・座標）確認 | — |
| `group_finalize` | 同時処理グループの受付を締め切り評価開始 | 代表者のみ実行可 |

### 前提となる考え方（宣言型モデル）

`set` の画像は**その人の個人開発領の「全体」**を表します。今回の画像に含まれない従前の範囲は**削除として扱われます**。「増やす分だけ送る」機能ではありません。参加者に「一部だけ変えたいのになぜ全体を送り直すのか」と聞かれたら、この宣言型モデルだからと説明してください。

画像は `image1`〜 の添付オプションで受け取ります（1枚＝1ゾーン。既定の本数は `settings.attachment_zone_count_default`、ゾーンの最大は16）。1回で送りきれないときは、同じ `group` を付けた追加の `set` で補えます。

### 形式審査（Bot形式審査）で何をチェックしているか

個人開発領の要件は**面積・保護区域・重複という機械的に一意に判定できる基準だけ**で構成されているため、運営の裁量を挟まずBotがその場で承認・却下します（類型C）。チェック項目は次の①〜⑧です。**1つでも満たさなければ却下**し、却下通知には**満たしていない条件をすべて**（該当ファイル名・具体的な数値つき、1件目で打ち切らない）示します。

| # | 条件 | 補足 |
|---|---|---|
| ① | 実データとして正しく読み込めるPNGであること | 拡張子だけでなく中身で判定 |
| ② | 画像サイズが 5000×5000px であること | ゾーン1枚のサイズ |
| ③ | 全ピクセルのアルファ値が `0` か `255` のみであること | 中間値（アンチエイリアスの縁）があると不合格。ペイントソフトの「なめらかな縁」をオフにして塗る必要がある |
| ④ | 申請面積が **250,000ブロック以下**であること | 面積＝クロップ後の合成画像の不透明ピクセル数（bboxの面積ではない）。複数ゾーンにまたがる場合は合成後の合計 |
| ⑤ | 特定保護区域と重複しないこと（ピクセル単位） | ※保護区域データが未整備の間は「登録0件」として扱い、この条件は常に通過します |
| ⑥ | 他の参加者の既存の個人開発領・仮承認中の範囲と重複しないこと（ピクセル単位） | **申請者自身の従前の範囲は判定対象から除外**（維持したいだけの再申告が自己重複で落ちないように）。重複時は重複相手の範囲と重複ピクセル数を提示 |
| ⑦ | ファイル名のプレイヤー名が、アカウント紐づけ（§2）に登録済みであること | 本人確認の照会先を特定するため |
| ⑧ | 申請範囲が旧ボーダー外にあること | — |

- **ファイル名**は `{ゾーン番号2桁}_{Minecraftプレイヤー名}.png`（例：`06_DAI_jin30.png`）。**最初の `_` より前がゾーン番号、それ以降すべてがプレイヤー名**（プレイヤー名に `_` を含むため）。このファイル名が「誰の申請か」の唯一の判断根拠です。
- 面積・座標はゾーン画像を実ワールド座標上に合成 → 透明な余白をクロップ（拡大縮小はしない）してから算出します。`loc1`/`loc2`（対角2点）はDynmap表示用のbboxにすぎず、範囲の定義そのものではありません。

参加者に「なぜ却下されたのか分からない」と聞かれたら、上の①〜⑧のどれに当たるかを却下通知の文面から読み取って説明してください。特に③（縁のアンチエイリアス）と④（面積オーバー）が実務上多い不合格理由です。

### `set` の3つの経路

| 経路 | いつこうなるか | 審査の流れ |
|---|---|---|
| **単独申請** | 自分の画像のみ・`group` なし | 即座に画像処理ジョブへ。①〜⑧を機械判定し、問題なければ**即時承認** |
| **代表者一括申請** | 複数プレイヤー分の画像・`group` なし | 形式要件を満たせば**「仮承認」**。各対象者にDMで確認ボタン（承認／取り下げ） |
| **同時処理グループ** | `group` 指定あり | 受付を蓄積するだけ。代表者が `group_finalize` を実行して初めて評価開始（下記） |

**代表者一括申請の確定**：

- `settings.deadlines.provisional_confirm_hours`（既定72時間）以内に本人が承認 → 正式承認（届出時刻は代表者の提出時刻に遡及。ここから24時間の撤回猶予が起算）。
- 無反応・取り下げ → **その人の分のみ**却下。他の対象者には影響しません。
- 対象者がアカウント未紐づけ、または既に処理中の届出がある場合は、その場で受付されません。
- 先行する仮承認が未確認・未却下の同一人物については、新規の `set` 受付を拒否します。
- 1回の `set` に含まれた複数人が互いに重複する場合は、**添付順（`image1`→`image2`→…）が提出順**。先に評価されて合格した申請は、後続の判定では「既存の個人開発領」として扱います。

### `delete`

`mcuser`（省略時は自分）・`group`（他者を対象にする場合は必須）。自分自身・`group` なしの**全部削除**は機械的に一意なので即時Bot形式審査。他人を対象にする削除は本人の権利が失われるため、必ず `group` を伴い、対象者の72時間本人確認を要します。**削除は復元不可。**

### 同時処理グループ（`group`）— 譲渡のための仕組み

**`group` は「複数の届出を、全部成立か全部不成立かのどちらかにする」ための束ね方**です。主な用途は**範囲の譲渡**です。

#### なぜ必要か（`group` なしだと何が起きるか）

Aさんが自分の範囲（の一部または全部）をBさんに譲るには、「Aさんの範囲を減らす（`delete` または縮小 `set`）」と「Bさんの範囲を増やす（`set`）」の**2つの届出**が必要です。これを別々に出すと:

- **Bさんが先に `set` を出す** → その範囲はまだAさんの個人開発領なので、条件⑥（他人の範囲との重複）で**必ず却下**されます。
- **Aさんが先に `delete` を出す** → 削除はその場で確定し**元に戻せません**。この直後にBさんの `set` が面積オーバーや画像不備で却下されると、**Aさんの範囲は消えたまま、Bさんは何も得られず**、しかも空いた土地を第三者に先取りされる恐れもあります。

`group` で束ねると **「全部成立」か「全部不成立（＝誰の範囲も変わらない）」** の二択になり、譲渡が途中で止まりません。

#### 手順（Aさん → Bさんへ全部譲渡する例）

1. AさんとBさんが、それぞれの届出に**共通の `group`（任意の合言葉。例：`jouto-abc`）**を付けて送ります。
   - Aさん：`/kaihatsu delete group:jouto-abc`（一部譲渡なら、譲渡後に残る範囲の全体画像を `set ... group:jouto-abc`）
   - Bさん：`/kaihatsu set image1:<譲受後の全体像> group:jouto-abc`
2. この時点では届出は**溜まるだけ**で審査は始まりません（合言葉が一致する届出を待っている状態）。
3. **最初にそのグループへ届け出た代表者本人**が `/kaihatsu group_finalize group:jouto-abc` を実行 → 受付を締め切って**まとめて審査**します。
   - Botは**先に削除を仮適用してから設定を審査**します。Bさんの範囲は「Aさんの範囲が消えた後の地図」に対して重複チェックされるので、上記「先に出すと却下」問題が起きません（削除評価→設定評価の順で、令和8年ルール第3号第8条第3項ただし書を自然に満たします）。
   - **どれか1つでも要件を満たさなければグループ全体を却下**（Bさんの設定が保護区域と重なっていれば、Aさんの削除も行われず元のまま）。
   - 締切後、削除対象メンバーには本人確認DM、設定メンバーは画像処理ジョブへ回ります。グループ全体の正式承認は、**関係者全員が72時間以内に承認**して初めて確定します。
- グループの `delete` で明け渡される予定の土地は、グループが解決するまで第三者の新規申請に対して「占有中」扱い（横取り防止）。競合した第三者の届出は却下せず保留し、グループ却下時は当初の届出時刻を維持して自動再審査します。

#### 「代表者一括申請」との違い

|  | 代表者による一括申請 | 同時処理グループ（`group`） |
|---|---|---|
| 目的 | **手間を減らす**（まとめ役が複数人分を代理提出） | **連動させる**（関連する届出を全部成立か全部不成立に） |
| 各届出の関係 | **独立**。1人却下されても他は進む | **一蓮托生**。1つ却下で全部却下 |
| 主な用途 | イベントで参加者の `set` をまとめて提出 | 範囲の譲渡（`delete`＋`set` の組） |
| 開始の合図 | 提出時点で自動的に仮承認・確認DM | `group_finalize` を代表者が実行するまで始まらない |

### 撤回（運営が触る主な操作）

単独申請の即時承認から `settings.deadlines.revoke_window_hours`（既定24時間）以内は、**運営者1人**がボタン操作＋理由入力（モーダル）で撤回できます。撤回すると効力を失い、**手動審査（類型A秘密投票）へ切り替えるタスクが自動起票**されます。撤回者名・理由は申請者にDM通知されます。参加者に「撤回されたら再申請していいか」と聞かれたら、通常は切り替わった手動審査の結果を待つ、と案内してください。

### 却下・重複・反映

- 重複却下時は**相手のMinecraft名を開示**する運用です。
- 削除された範囲は復元しません。代わりに確認画像で削除範囲を強調表示し、警告を充実させています（誤操作は再申請で対応）。
- 正式承認が確定すると、**Dynmapへの反映まで自動**で行われます。可視化ロジック自体は既存のDynmap＋自作JSを流用しています。

## 2. `/authorise`・`/modauth`・`/whoami`（アカウント紐づけ）

**かんたん説明**：`/authorise` は参加者本人による初回登録、`/modauth` は運営による登録・修正・解除、`/whoami` は本人による確認用です。紐づけの主キーはMinecraftの**UUID**（ユーザー名は変わりうるため）。

**詳細**：

- **`/authorise mcuser`**：実行資格は「人民」または「仮参加者」ロール保有者（`settings.roles`）。却下条件は4種類 — ①ユーザー名が実在しない、②既に他のDiscordアカウントに紐づけ済み、③実行者が既に別アカウントを紐づけ済み（＝自己申告での上書き不可）、④実行資格ロールなし。
  - **同一UUID・同一Discord IDの `inactive` レコードがある場合は、条件②③より先に `active` へ復元**します（再参加時の扱い）。
- **`/modauth link discord:<対象> mcuser:<名前>`**：運営者ロール限定。却下条件①②④は `/authorise` と同じですが、**条件③（本人による上書き）は運営の判断で上書き可能**（確認ボタンを挟み、旧アカウントはホワイトリストから削除）。すべての実行が実行者名・対象・変更前後の値とともに**監査ログへ記名で永久保存**されます。
- **`/modauth remove discord:<対象>`**：紐づけを解除し、ホワイトリストからも自動削除。
- **`/whoami`**：本人にのみ表示される紐づけ状況確認。相談を受けたらまず本人にこれを実行してもらってください。
- 紐づけ成功時はホワイトリストへ自動追加、脱退・ロール喪失時は自動削除（Crafty Controller REST API経由のコンソールコマンド送信。RCONの新規開放やサーバーファイルの直接編集はしません）。

## 3. `/modvote`（運営の秘密投票・類型A）

**かんたん説明**：運営内で賛否を問う**匿名**の秘密投票です。`start`＝通常投票、`quick`＝短縮投票（同時会議での即決用）、`status`＝状況確認、`end`＝即時終了、`hogokuiki_build`＝保護区域内の建築・採掘承認の専用入口。

### サブコマンド

| サブコマンド | 用途 | 実行資格 |
|---|---|---|
| `start` | 通常の秘密投票を開始（既定 `settings.deadlines.vote_hours`＝24時間） | 「運営」ロール |
| `quick` | 短縮投票を開始（`settings.deadlines.quick_vote_minutes`） | 「運営」ロール |
| `status` | 進行中投票の状況確認 | 「運営」ロール |
| `end` | 期限前に即時締切・集計・結果投稿 | 「運営」ロール |
| `hogokuiki_build` | 保護区域内建築・採掘の承認投票（内部は `start` 経路） | 「運営」ロール |

**詳細**：

- `approval_key` は `settings.approval_types`（§5.5の分類表）から選び、`subject`（件名）を必須入力。本人除外が必要な事項（処罰・解任、再任等）では `target` が必須です。
- **定足数の計算方式（`quorum_type`）は事項ごとに異なります**：
  - `voters_majority`：棄権者を除く投票者数の過半数（通常の秘密投票の既定）
  - `supermajority_voters`：同じ分母に対する特別多数（閾値は `threshold`）
  - `total_majority_excl_abstain`：明示的棄権者を除く運営者**総数**の過半数（`quick` は常にこれに固定）
  - `supermajority_total`：運営者総数に対する特別多数
  - `unanimous_excl_target`：対象者本人を除く全会一致（処罰・解任、再任）
  - `other_majority`：分類表にない案件を通常多数決で回すための汎用枠（`voters_majority` と同じ計算。特定の条文には対応しない）
- **母数**は「運営」ロールの実際の保有者から算出し、休暇中（`/staff leave`）の者と `exclude_self` 対象の本人を除外します。
- 投稿先は `settings.channels.vote_hall`（**投票専用チャンネル「投票場」**。督促Lv3・ダッシュボード等の他の運営通知と混ざらないよう分けています）。賛成／反対／棄権のボタンで投票し、**ボタン押下への応答はephemeral**なので秘密投票として成立します。
- **締切処理は `*/10 * * * *`（10分おき）のCron**で実行するため、締切時刻経過後**最大10分の遅延**が生じ得ます（仕様どおり。短縮投票でも同じ）。急ぐ場合は `end` で即時終了。
- `end` は `vote_id`（autocomplete対応。件名の部分一致で「件名（#id）」形式の候補表示）を指定。1人の実行で即座に締切・集計・結果投稿まで行います（承認・却下の判断自体は投票結果に委ねるためC-3に抵触しません）。Cronやボタン起点処理との競合は `votes.status='open'` を条件とした排他制御で防止。
- `hogokuiki_build` は `approval_key` が内部的に `protected_area_build_approval` 固定で、`area_name`・`description`・`area_image` から件名を組み立てて通常の秘密投票経路に乗せます。

## 4. `/vote`（参加者投票・類型A）

**かんたん説明**：参加者の賛否を問う**匿名**の秘密投票です。**開始・終了は運営者が行い**、投票権は参加者（「人民」ロール）にあります。短縮投票（`quick`）はありません。

### サブコマンド

| サブコマンド | 用途 | 実行資格 |
|---|---|---|
| `start` | 参加者投票を開始 | 「運営」ロール（`/modvote` と同じ） |
| `status` | 状況確認 | 誰でも（参加者含む） |
| `end` | 期限前に即時締切・集計 | 「運営」ロール |

**詳細**：

- **母数は「人民」ロール（`settings.roles.hito`）保有者数**。休暇制度（除外）は適用されません（運営者専用の制度のため）。
- `approval_key` は `settings.participant_approval_types` という**別テーブル**の分類表から選びます（`/modvote` の `settings.approval_types` とはキーが一部重複しても競合しません）。定義済み事項：
  - 参加者となる権利の取得（元参加者）
  - ワールドデータの外部利用（参加者限定）
  - ワールドデータの外部利用（非参加者含む・特別多数）
  - ルール改正
  - その他
- **「ワールドデータの外部利用（非参加者含む）」** は `total_majority_incl_abstain`：棄権者も母数に含めた**参加者総数に対し、厳密に半数を超える賛成**が必要（「ちょうど半数」では可決しません）。
- **「ルール改正」** は運営側の特別多数とは揃えず、通常の `voters_majority` 相当です。
- 期限は運営投票と同じ `settings.deadlines.vote_hours` を流用。投稿先は `settings.channels.participant_vote_hall`（`vote_hall` とは別の専用チャンネル）。
- `status` は参加者含め誰でも実行可（候補表示のゲートなし）。`end` は運営者のみ候補表示・実行可。

## 5. `/kyoka`・`/umetate`（記名許可・類型B）

**かんたん説明**：秘密投票ではなく「**誰が賛成したか公開される**」記名式の許可要請です。`/kyoka` は技術者コマンド使用など運営内の許可、`/umetate` は参加者も使う海の埋立て許可。

**詳細**：

- **`/kyoka kind subject description`**：`kind` は `settings.approval_types` のうち `method: "B"` のもの（現状「技術者のコマンド使用（利益増進目的）」）。`subject` 必須、`description` 任意。
- **`/umetate image description`**：`image` または `description` のどちらか必須（両方省略は却下）。内部的に `approval_key: "land_reclamation"` 固定で `/kyoka` と同じ経路を通ります。
- どちらも要請は `settings.channels.unei_only`（運営専用チャンネル）に投稿され、OK/NG/取り下げのボタンが付きます。**OK/NGを押せるのは「運営」ロール保有者のみ**、取り下げは申請者本人のみ。
- 成立条件は `required_count` 人以上のOK（`/umetate` は既定2人）。成立すると申請者へDM通知、関連タスクが自動的に完了扱いになります。
- **記名・公開・永久記録**である点が秘密投票（類型A）との最大の違い。参加者に「なぜ埋立て許可だけ誰が賛成したか分かるのか」と聞かれたら、この記名許可の仕組みだからと説明してください。

## 6. `/task`（運営内タスク管理）

**かんたん説明**：運営内のタスクを起票・完了・辞退・保留・一覧表示します。`assignee` を指定しなければBotが自動で担当者を割り当てます。全サブコマンド運営者ロール必須。

### サブコマンド

| サブコマンド | 用途 | 誰が実行できるか |
|---|---|---|
| `add` | タスク起票 | 運営者 |
| `done` | 完了。`evidence`（根拠・メッセージリンク等）必須 | 運営者。ただし共同確認タスクは担当者・共同確認者のみ |
| `decline` | 辞退（理由不要）。自動再割当が走る | そのタスクの担当者本人のみ |
| `hold` | 保留。`resume_at`（`YYYY-MM-DD`）必須。当日に自動で「割当済」へ戻る | そのタスクの担当者本人のみ |
| `list` | 自分に残る未完了タスクと期限（本人にのみ表示） | 運営者 |

`done`・`decline`・`hold` の `task_id` はautocomplete対応（タイトル部分一致で「タイトル（#id）」表示）。`decline`・`hold` の候補はその担当者に割り当てられたタスクのみ。

### `add` のオプション

| オプション | 内容 |
|---|---|
| `title` | **必須** |
| `assignee` | 省略時は自動割当アルゴリズムが動く |
| `priority` | high / medium / low（既定 medium） |
| `tag_1`〜`tag_3` | §4.4の9種類の必要タグから選択式で最大3つ |
| `requires_technician` | 技術者＝OP保持者限定か |
| `required_permission_tier` | admin / broad / standard（実行権限レベルの下限） |
| `controversial` | 論争性が高いか。付けると共同確認者を自動追加 |
| `estimated_load` | 1〜5 |
| `due_at` | `YYYY-MM-DD-hh-mm`・日本時間（省略時はBot既定の目標期限） |

### 自動割当アルゴリズム（LLM不使用）

1. **ハード条件で候補を絞り込み**：稼働中／休暇中でない／技術者要件／権限レベル／同時対応上限未満。
2. **残った候補をスコアで順位付け**：
   `タグ一致度×w1 − 弱点タグ一致度×w1' + 空き余力×w2 + 完了実績×w3 + 稼働時間帯一致×w4 + 直近連続割当ペナルティ×w5`
   （重みは `settings.assignment_weights`）
3. **同点、またはタグ一致度が全候補で閾値未満の場合**は「未割当・要手動対応」として運営チャンネルに通知。この微妙なケースの最終判断だけは、**ログなどの情報からLLMが判断**します（機械的なスコアだけでは決めきれないケースに限定）。

### 共同確認（`controversial`）

論争性ありのタスクには次点候補が共同確認者として自動追加され、**担当者と共同確認者の両方が完了操作**をして初めて正式完了。片方だけなら「もう一方待ち」で保存されます。

### `decline` の挙動

辞退すると自動再割当が走り、直前の辞退者は候補から除外されます。再割当に失敗した場合は未割当に戻り、運営チャンネルへ手動対応依頼が飛びます。

## 8. `/subaccount`（運営サブ垢の連携）

**かんたん説明**：サブ垢を使っている運営者が、サブ垢からでも運営コマンドを使えるようにする連携コマンドです。連携済みサブ垢での操作はすべて「メイン垢が行ったもの」として記録されます（投票の一票・記名許可の署名を含む）。

### サブコマンド

| サブコマンド | 用途 | 実行資格 |
|---|---|---|
| `link user:<サブ垢>` | 連携リクエスト。サブ垢へ本人確認DMが飛ぶ | **メイン垢（実際に「運営」ロールを持つ本人）のみ** |
| `unlink user:<サブ垢>` | 連携解除 | そのサブ垢を連携したメイン垢のみ |
| `list` | 自分に連携中のサブ垢一覧（連携済み／確認待ちの別） | メイン垢 |

**詳細**：

- 前提：対象のサブ垢に**あらかじめ「運営サブ垢」ロール（`settings.roles.unei_sub`。運営ロールとは別）**を付与しておく必要があります。運営ロールと部門ロールと同様、自動付与ではなく手動の役割分担です。
- `link` 実行後、サブ垢が `settings.deadlines.subaccount_confirm_hours`（既定24時間）以内に許可ボタンを押して初めて連携成立。無回答で期限切れならリクエスト無効、`link` からやり直し。
- 1人のメイン垢に複数サブ垢を連携できますが、**1つのサブ垢が同時に連携できるメイン垢は1つだけ**。他の運営者が既に連携済み・確認待ちのサブ垢は指定できません。
- 連携済みサブ垢から運営コマンドを実行すると、実行資格判定（「運営」ロール必須の判定）を代わりに満たし、投票の一票・記名許可のOK/NG署名・監査ログの記録者名などがすべてメイン垢のものとして扱われます。**同じ人が2アカウントで同じ投票に2票入れることは起きません**（同一人物として集計）。
- 「運営サブ垢」ロールがあっても連携未完了なら、運営コマンドを実行しても「先にメイン垢で /subaccount link を実行してください」（確認待ちなら「サブ垢宛てのDMのボタンから確認を完了してください」）と表示され受け付けられません。
- **参加者向け `/vote` の一票行使は対象外**。サブ垢に「人民」ロールを付与しない限り、サブ垢は参加者投票には参加できません（この連携は運営コマンド専用の仕組み）。
- 他の運営者に「なぜ自分のサブ垢で運営コマンドが使えないのか」と聞かれたら、上記の `link` 手順（本人確認DM）が必要と案内してください。

## 10. 参加者から聞かれやすい質問への回答例

- **「なぜ削除は復元できないの？」** → 誤操作対策は事前（確認画像での警告表示の充実）に寄せる設計判断で、事後の復元は行いません。再申請で対応してもらってください。
- **「投票で自分の投票内容は誰かに見られる？」** → 見られません。ボタン応答はephemeralです（`/modvote`・`/vote` とも類型A＝秘密投票）。
- **「なぜ埋立て許可は誰が賛成したか分かるの？」** → 記名許可（類型B）という、秘密投票とは別の仕組みだからです。誰がOKを押したかは公開・記録されます。
- **「タスクの担当者はどう決まるの？」** → タグ一致度・空き状況・実績などをスコア化して自動選定します。僅差や判断が難しいケースだけ、ログなどの情報をもとにLLMが最終判断します。
- **「投票の締切がちょうどの時刻に来ない」** → 締切処理が10分おきの定期実行のため、最大10分程度遅れることがあります（仕様）。
- **「一部だけ変更したいのに、なぜ個人開発領の全体を送り直すの？」** → 宣言型モデルだからです。今回の画像に含まれない範囲は削除扱いになります。
- **「個人開発領の申請が撤回された。再申請していい？」** → 撤回で手動審査（秘密投票）に切り替わっているので、通常はその審査結果を待ってください。
